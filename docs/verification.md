## Terms of use

**Outcome for a personal build: permitted with limits, as an operational reading of the public sources.** The integration can be built on the installed CLIs and the official login the user already performed. It uses one active account per provider, copies no credentials, offers no profile switcher and performs no automatic account switching. It does not present subscription limits or US dollar estimates as a billing promise. The authentication method and the possible billing stay `unknown` until verified for the concrete session.

[Anthropic's plan guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), updated on 7 October 2026, states that the Agent SDK, `claude -p` and third-party applications can still use subscription limits. The [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) states that, without prior approval, third-party developers may not offer claude.ai login or its usage limits in their own products. The sources do not settle the case of distributing this extension, so **distribution with a Claude login or Claude usage limits is outside this outcome** and needs a written clarification from Anthropic or a different integration with declared billing. The extension will not offer a Claude login of its own.

For Codex, the [CLI authentication documentation](https://learn.chatgpt.com/docs/auth) describes the official ChatGPT login with credentials stored in `CODEX_HOME` or the system keyring. The [Sign in with ChatGPT guide](https://developers.openai.com/siwc/quickstart) distinguishes plan use in open-source applications from selected commercial partners, and the [app-server guide for that flow](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) expects the application's own OAuth and token handling. Those are different models from personal use of an already authenticated CLI. A distribution path must be chosen and verified separately, and the CLI's token file will not be used as a shortcut for an in-product login.

Before distributing to other people: fix the distribution and authentication model, obtain Anthropic's clarification if claude.ai login or limits are to be offered, verify eligibility for the chosen OpenAI path, and record that outcome. The personal outcome is not an approval for a distributed product.

#### Static review of 22 October 2026, and what it changed

An independent static review of the Strict code and tests found four defects that the test suite did not cover. All four are fixed, each with a regression case:

1. **A false `completed_clean` was reachable.** The snapshot digest covers reviewable changes only, and the phase checked reviewability just before the first Codex review. An unsupported path appearing later — a symlink after the approvals, for instance — left the digest untouched and the task could complete. Reviewability is now checked at every checkpoint that rebuilds the perimeter, and the state machine admits `review_failed` from those states.
2. **Protected path names reached the Output Channel.** The failure message naming them was emitted as an event, and the extension logs every event message to the channel. Failures now carry a separate, path-free message for the event stream; the full message stays in the chat and the report. Filesystem errors from the capture are redacted the same way, since they can quote a path.
3. **A change in a file above the 1 MiB snapshot limit could be invisible.** Those files were not hashed and the comparison fell back to size, mode and modification time, which is not evidence of content at all. Every included file is now hashed, large ones without retaining their bytes; they are still not reviewable, so such a change blocks completion instead of passing unseen.
4. **The reader could follow a symlink swapped during the scan.** `lstat` followed by a read by path is a time-of-check/time-of-use hole. Files are now opened with `O_NOFOLLOW` and the open handle is checked against the identity `lstat` saw.

The same review raised four smaller deviations, also fixed: the lifecycle marker is written before the first provider request of phase A rather than at the start of phase B; a marker that does not match the schema now blocks a new task like a foreign one; the review-cycle count is tracked and reported instead of always reading zero; and the report no longer claims the inventory ceiling stopped a task that in fact continued, nor that a policy-excluded change blocks completion.

#### Second static review, and what it changed

A follow-up static review found that the scanner still had three ways to read outside its limits or to reach a clean completion over an unreviewed change. All three are fixed:

5. **A directory swapped for a symlink could take the scan outside the workspace.** `O_NOFOLLOW` protects the last path component only, and `readdir` resolves the parents by name. Node cannot read a directory through a descriptor, so this cannot be prevented; it is now detected. Each directory is opened with `O_NOFOLLOW | O_DIRECTORY`, its inode identity is recorded, and the same path is checked again once its children have been read. A mismatch aborts the whole capture with `workspace_changed`, so nothing read through a swapped parent reaches a provider or the report. The earlier claim that a swap "surfaces as a changed perimeter" was not backed by code; it is now.
6. **The 64 MiB ceiling counted the size `lstat` reported, not the bytes read.** A file that grew after `lstat` could exceed the ceiling, and a file that started under 1 MiB could also have its chunks retained. The budget was changed to count the bytes the reader consumes; a file whose length no longer matches what `lstat` saw aborts the capture; and retention stops as soon as a file grows past the snapshot limit. *(The aggregate ceiling itself was removed on 23 October 2026 — see the section on the scan byte ceiling below. The length check and the retention rule remain.)*
7. **A symlink already present at the baseline could be retargeted unseen.** Unsupported paths kept only size and modification time, so a target of the same length with the timestamp restored compared as unchanged. They now also carry inode identity and, for a symlink, the SHA-256 of its target read with `readlink`, which never follows it; a link whose target cannot be read counts as changed.

Regression cases cover each: a symlink retargeted to another path of the same length is reported as a changed unsupported path and makes the snapshot unreviewable; a directory replaced by a symlink to an outside folder is reported as changed and no outside content appears in the snapshot; and a file above the per-file snapshot limit is hashed and never retained. *(The third case originally asserted that the aggregate ceiling stopped the baseline; it now asserts the opposite, that the baseline completes.)*

#### Third static review, and what it changed

A third static review found that the identity check from the previous round could be bypassed, and that a concurrent write of the same length was still invisible. Both are fixed:

8. **Swap and restore defeated the identity check.** `readdir` ran on the directory's path, so a parent replaced after the enumeration could redirect the reads of its children; restoring the original directory before the final check made the inodes match again and the capture succeeded with outside content in it. The traversal no longer resolves any child by the parent's name: each directory is opened with `O_NOFOLLOW | O_DIRECTORY` and every entry below it — enumeration, `lstat`, file open and recursion — is resolved through `/proc/self/fd/<fd>`, which gives Node the `openat` semantics it does not expose. A parent swapped at any moment cannot redirect a single read, so this is prevented rather than detected. Where `/proc` is not available the capture fails with a stated reason instead of falling back to path resolution.
9. **A same-length rewrite during the read went unnoticed.** Counting the bytes read cannot see a write that preserves the length. Each read is now bracketed by a high-precision `fstat` on the open handle, comparing size, `mtimeNs` and `ctimeNs`: `ctime` cannot be set from user space, so any write during the read moves it, and restoring `mtime` moves it too. A probe confirmed the behaviour outside the suite — a 1 MiB rewrite landing in the middle of a 24 MiB read ends the capture with `workspace_changed`.

Two cases hold the invariants under real contention: a directory swapped and restored repeatedly during the capture of a 400-file tree, which asserts that at least one swap completed and that no outside byte appears in the snapshot; and a file rewritten at the same length while it is read, which asserts the capture either fails with `workspace_changed` or still reports that file as changed on the next capture. Neither depends on winning a race to pass.

#### Fourth static review, and what it changed

A fourth review found three windows the previous round left open. All three are fixed:

10. **The root was not anchored between captures.** The baseline recorded the root's path and digest, not its inode. Pinning the descendants of an open root says nothing about whether the opened root is still the one the baseline scanned: a root, or any parent of it, replaced between two captures would have been scanned as if it were the same tree. The scan now records the root's inode identity and every later capture proves the opened root matches it, failing with `workspace_changed` otherwise.
11. **A file swapped for a FIFO could park the capture.** `open()` on a FIFO waits for a writer, and the type check happened only after the handle existed. The open now carries `O_NONBLOCK`, which changes nothing for a regular file and makes the swap impossible to use as a stall.
12. **A `chmod` between `lstat` and `open` could be recorded with stale bits.** The permission mode came from the earlier `lstat`. It now comes from the opened file, and a mode change during the read joins size and the timestamps in the bracket that ends the capture.

Regression cases: the root renamed aside and replaced by another directory holding a sentinel file fails the capture with `workspace_changed` and never names the sentinel; a file whose executable bit changes is recorded with the mode of the file actually opened; and a FIFO in the perimeter is classified as an unsupported special file with the capture completing well inside its timeout.

#### Fifth static review, and what it changed

The fifth review moved off the scanner and onto the protocol, the validators and the report. It found four defects, all fixed:

13. **The checks could pass on a digest that was never the one approved.** A check writing inside the perimeter changed what had to be reviewed, and its result was then recorded against the new digest and carried forward, so a clean completion was reachable without the checks ever having run on the final snapshot. A check round is now repeated on the new state until the checks leave the digest where they found it; each round records the digest it actually ran against; and checks that never stabilise end the task with `checks_failed` instead of a review.
14. **The human approval did not re-check the workspace on its way back.** The baseline was verified before the gate but not after it, and phase B called Claude before its first capture, so a change landing while the approval was open could enter the work unseen. The approval now re-checks the baseline before it is accepted, and phase B proves the perimeter still matches the baseline before the first write.
15. **A protected path could still reach the Output Channel.** Refusing a plan that names, say, `.env` put the path in the reason, and a failure without a message written as safe forwarded it to the event stream, which the extension logs. Every failure now defaults to an event message built from its reason code; only a message explicitly written as safe is used instead. The same rule now applies to phase A, whose events no longer carry provider prose or the text of a plan question — both still reach the chat through their own messages.
16. **A finding reported again kept its first details.** Only status and digest were refreshed, so the report and the correction request could show a stale file, line, severity, evidence or blocking flag. A re-reported finding now replaces its details entirely and drops the earlier resolution.

Regression cases: a formatter that rewrites a reviewed file once makes the checks run twice, with the reviewed and approved digest being the one the second round checked; a check that rewrites on every run ends the task without a review; a change landing between approval and first write stops phase B before any provider call; a finding re-reported with a new line, severity and blocking flag is carried with the new details; the plan refusal for a policy-excluded path keeps it out of the event stream; and phase A keeps an objection's text and a question's text out of its events while the chat still receives the question.

#### Product decision: credential-shaped paths, and the sixth review round

The owner retired the protected-path finding on 23 October 2026. In Strict, `.env` and `.env.*`, `.ssh/`, `.aws/`, `.gnupg/`, `.npmrc`, key and certificate files are no longer a category: they are scanned, hashed, diffed and sent as provider context like any other file. The metadata-only inventory, its per-task ceiling, its report section and the failures that stopped a task over those paths are removed. **The consequence, recorded deliberately: a secret stored in the opened folder is visible to Claude and Codex and appears in the chat report.** Balanced keeps refusing those paths, so the two modes differ here by design, and a regression case pins both halves.

The same round reviewed the areas the earlier rounds had not: the CLI adapters, the task composer and the sidebar path. It produced these fixes:

17. **The sidebar render crashed on a stale element id.** `renderModeControls` toggled a row that no longer existed in the element table, which threw and took the whole render with it — five webview cases caught it. The reference is gone and the remaining toggle is optional, so one missing node can no longer blank the sidebar.
18. **A structured output delivered as a JSON string was rejected.** The Claude envelope reader re-encoded whatever it found, handing the validator a quoted document when the CLI returned a string. A string now passes through unchanged.
19. **Empty usage was reported as a measurement.** A turn that reported no tokens and no cost still produced a metrics entry, which the report printed as usage with unavailable numbers. Nothing reported is now reported as nothing.
20. **An output-limit failure was mapped to a generic protocol error** in both adapters; it now says what happened.
21. **The report called a dirty repository clean.** "Changes already present before this task" came from comparing the baseline with itself, which is empty by construction — the Strict baseline *contains* that work. It now comes from Git's own status at task start, and a folder without Git simply lists nothing.
22. **An unexpected throw could leave the marker claiming an active task.** Both phases report failures as results, so reaching the composer's catch means something threw where nothing should; the marker is now written as interrupted and the task returns a failed result instead of propagating.
23. **The approval card could invent a suggested ceiling.** The controller replaced an absent suggestion with the configured value, so the sidebar showed a recommendation that was not one. The data is passed through unchanged.

A cancellation defect found in the same round — the Strict request carried no signal, the runtime created its controller only after the gate and Git preflight, and the capability probes ignored the signal — was already fixed in the working tree when this round started; the tests here cover the probe half of it.

#### Seventh static review, and what it changed

24. **The baseline was not anchored to the directory the call resolved.** `createStrictWorkspaceChanges` resolved the root with `realpath`, then let the scan record whatever identity its own `open` happened to see. A parent replaced between those two steps would have anchored every later capture to the tree the scan read, with nothing ever flagging it. The identity now comes from the resolved root and the baseline scan has to prove it opened that directory.
25. **An unreadable Git status was reported as a clean tree.** The list of work already in the repository came from Git with every error turned into an empty list, so "Git could not answer" and "nothing was changed" looked identical in the report, and a cancellation during that read was swallowed with it. The answer now keeps its provenance — `git`, `no_repository` or `unavailable` — the report says which, and a cancellation propagates to the task instead of being reported as an empty list.

Regression cases: a root swapped repeatedly while the baseline is taken either fails the baseline or produces one with no planted content in it; a folder without Git, a repository that stops being readable after the baseline, and a healthy dirty repository each produce their own provenance; an aborted signal makes the read throw rather than return nothing; and the report prints a different sentence for each of the three cases.

#### Eighth static review, and what it changed

26. **The root was resolved twice.** `realpath` was followed by an `lstat` on the same path, so a parent replaced between the two gave the expected identity of an outside directory, which the scan then matched. The root is now opened once, without following links, and the baseline, every capture and every descendant are reached through that descriptor — the root is pinned exactly like its children, and the only remaining window is between `realpath` and that single open. The path is still compared with the pinned identity at each capture, so a root replaced later is reported rather than scanned from the old inode. The descriptor is released when the task ends.
27. **A cancellation became an internal error.** A cancellation raised while reading Git reached the composer's general catch and was reported as `failed` with `internal_error`. The catch now recognises it and returns a `cancelled` result.
28. **"Not checked" read as "Git said it was clean".** `preExistingStatus` is absent on the paths that end before the workspace is read — a busy repository, a marker this window does not own — and the report printed the clean-tree sentence for it. An absent value now says the task ended before Countersign looked, and claims nothing.

Regression cases: a workspace whose **parent** is swapped for a link to a decoy tree, repeatedly, while the baseline is taken, either fails or produces a baseline with no decoy content; a task cancelled on its way in returns `cancelled` rather than an internal error; and a task stopped on a foreign marker reports that it never looked at the workspace.

#### Ninth static review, and what it changed

29. **The root descriptor leaked on one exit.** A cancellation raised while Git was read escaped `createStrictWorkspaceChanges` after the root had been opened, so the descriptor was never closed. Ownership is now explicit: the function holds the descriptor until a workspace is handed back, and every other exit — failure, cancellation, or a throw from the Git read — closes it in a `finally`.
30. **Only the scanner was bound to the open root.** Git and the provider processes still used the path, so a root replaced between a check and a spawn would have moved them into the substitute tree; a check before the spawn only narrows that race. Every root-bound process now runs with its working directory set to the root reached through its descriptor: the Git status and HEAD reads, the Claude CLI and SDK turns, the Codex `exec` turns and the configured local checks. The path is still what the prompts and the report name, so the model sees the workspace path and the process runs in the pinned directory.

Regression cases, all deterministic: a signal that reads as live during the scan and as cancelled when Git runs produces a `cancelled` result and leaves the process with exactly the descriptors it started with; a successful creation holds one more descriptor and `close()` releases it; and with the root path renamed aside and a decoy put in its place, a process launched with the pinned working directory reads the original file while `git rev-parse --show-toplevel` answers for the original repository, not the decoy. The adapters are covered separately: both spawn with the pinned working directory while the prompt still names the workspace path.

**The limit of this boundary, stated rather than implied.** The pinned working directory is resolved through `/proc/self/fd/<fd>`, which is Linux-only; Strict is a Linux-only mode, and `scanStrictWorkspace` already fails with a stated reason where `/proc` is absent. A process is bound to the directory at `chdir` time, before `exec`; if a provider or a check later re-resolves the workspace by its path on its own, Countersign cannot prevent it from reaching a substitute tree. What is guaranteed is the directory those processes start in, and that the scan, the digest, Git's own reads and the checks all use the same pinned root.

#### Tenth static review, and what it changed

31. **Git still re-resolved the root.** The pinned root was handed to `preflightGit`, which turned it into an ordinary path with `realpath`, used that path as a working directory, then took Git's own `rev-parse --show-toplevel` output and used *that* path for the status read; the HEAD read followed the same route. A root replaced after any of those resolutions would have redirected the commands the caller had pinned. Strict now has its own Git reader: every command runs with its working directory set to the pinned root, and no path from `realpath` or from Git's output ever becomes the working directory of the next command. The reported top level is used as identity only, and it has to be the very directory the scan pinned — compared by inode — or Strict does not treat the workspace as a repository. Git is read once, with the baseline, which is exactly when "already present" is defined. Balanced keeps `preflightGit` and `readGitStatus` unchanged.

The only remaining Git call on a path is the pre-task probe that decides whether to warn "this folder has no Git repository root". It is best-effort: it supplies neither the status, nor the HEAD, nor the working directory of any Strict command, and the Codex `--skip-git-repo-check` flag no longer depends on it, because Codex runs in the pinned root, which it cannot recognise as a repository on its own.

32. **A cancellation during the Git read was reported as an unreadable perimeter.** `readStrictGit` rethrows a cancellation, and the creation mapped it through the generic failure path to `baseline_unavailable`. It now returns a `cancelled` failure, and the descriptor is released by the same `finally` as every other exit. The earlier regression did not exercise this: its fake signal flipped during the scan, before Git ran. It now uses a signal that stays live while the perimeter is scanned — which starts no process — and reports a cancellation once the first Git command has started, so the next one is refused inside the Git read. The case asserts the `cancelled` code, that a process really started, and that the descriptor count returns to its starting value; a companion case asserts that `runStrictTask` reports the task as `cancelled` and that no marker was written.

Regression case, deterministic on the real flow: a repository and a decoy repository are both created with uncommitted work, the baseline is taken on the first, then the root path is renamed aside and the decoy is moved into its place. Read at that point, `readStrictGit` reports the original repository's top level, its HEAD and its dirty entries, and none of the decoy's. Supporting cases cover a folder without a repository, a repository broken after the baseline (the answer recorded at baseline time stands), and a repository whose status cannot be read, which reports `unavailable` rather than a clean tree.

#### Final sweep across the declared guarantees

A last pass went over the whole Strict path against each guarantee — descriptor ownership, the scanner and captures, the Git reads, the working directory of the Claude CLI and SDK, Codex and the local checks, cancellation and cleanup, every transition that can reach `completed_clean`, the events and the report. It found three more defects, all fixed:

33. **A closed workspace still captured.** A descriptor number is reusable once released, so `/proc/self/fd/<fd>` would have pointed at whatever took it. A closed workspace now refuses to capture and says so.
34. **Phase B events still quoted the providers.** Phase A had been swept; phase B had not. A Codex non-approval, a Claude rejection and an invalid-response note carried provider prose and validator text into the event stream, which the Output Channel logs. The events now state what happened and point at the chat report.
35. **The completion claimed checks that were never configured.** Both the phase B event and the task's own message said "the configured checks passed" even when no check existed. They now say that none was configured and none was run.

The same pass confirmed, without finding a defect: the SDK tool policy still resolves correctly through the pinned working directory, because both the root and the tool's target are resolved with `realpath` before being compared; every directory and file handle in the scanner is released in a `finally`; and `completed_clean` is reachable only from `awaiting_final_consensus`, after a check round that left the digest where it found it, a reviewable snapshot, an explicit Codex approval, an unchanged digest, an explicit Claude approval, another unchanged digest and no open blocking finding.

**Which cases prove a branch, and which only observe a nearby state.** These prove the branch: the big-file content change with preserved size and timestamps; the retargeted symlink; the root replaced between captures; the closed workspace; the cancellation landing inside the Git read, which asserts a process had started; the Git boundary with a decoy repository; the check round that re-runs and the one that never stabilises; the change between approval and first write; the re-reported finding; the event-redaction cases; and the completion wording with and without a configured check. These only observe a state near the branch, because the race they protect against cannot be staged deterministically in-process: the directory and parent swaps during a scan, the concurrent same-length write, the FIFO substituted between `lstat` and `open`, and the permission bits changed in that same window. They hold the invariant under real contention, and they are listed here as what they are.

#### Product decisions of 23 October 2026: no per-task changed-file ceiling, catalogue-driven effort levels

The owner removed the per-task changed-file ceiling from Strict. It is gone from Turn settings, the approval card, the request contract, the limits, the validators, the scanner, the report, the tests and the documentation, and no equivalent per-task cap replaced it. The technical limits at that point were: 20,000 scanned files, 64 MiB scanned, 1 MiB per file in the snapshot, a 256 KiB diff and a 16 KiB new file. *(The 64 MiB scanned ceiling was removed the same day — see below.)* The plan's own file estimate survives as information shown at the approval gate, and a regression pins that approval needs no ceiling while the estimate still reaches the gate.

The owner also made the effort menus follow the provider catalogues. The static allowlists are gone from the configuration validator and from the sidebar: configuration now checks the shape of a level, not its membership in a list kept here, and the sidebar offers exactly the levels the selected model's catalogue reports, with the catalogue's labels, sending the chosen value to the provider unchanged. A stored model or level the catalogue no longer offers no longer blocks a turn: it falls back to the CLI default with a notice in the sidebar and in the Output Channel. The sidebar now preserves that saved choice visibly, including after a model switch or window reload, so a temporarily unavailable catalogue does not erase the user's preference.

Three regressions cover the catalogue behaviour, and each exercises the branch rather than a nearby state: a catalogue carrying a level this build has never contained (`ultra`) offers it, labels it as the catalogue does and sends it unchanged; two models with different level sets re-populate the menu on a switch and drop an unsupported saved level with the notice visible; and a model that disappears from a later catalogue produces the fallback notice naming it. The configuration cases assert that an unknown-but-well-formed level is accepted and a malformed one is still refused.

The verified-version checks are untouched, and the documentation says what the behaviour is: the menus update from the catalogue a **verified** version exposes, which is not a promise about versions this project has never verified.

#### Product decision of 23 October 2026: the scan byte ceiling is gone

A real folder — roughly 304 MiB of files included by the Strict policy — ended its task before phase A with `scan.maxScannedBytes`, telling the user to open a smaller folder. That ceiling was not a limit of the Claude or Codex CLIs; it was this project refusing to do the job it exists to do. It is removed.

**What changed.** `STRICT_SCAN_CAPS` no longer holds `maxScannedBytes`, and `scan.maxScannedBytes` is gone from the breach identifiers, the scanner, the task's next-action text, the limits test and the report. Nothing in Strict now fails because of the number of bytes a scan read. The remaining scan ceilings are unchanged: 20,000 scanned files, 1 MiB per file in the snapshot, a 256 KiB diff and a 16 KiB new file.

**What replaced it, and what it is not.** Hashing was never the problem — it streams, and a 304 MiB perimeter costs a few hundred milliseconds of SHA-256. Memory was: the scanner kept the bytes of every included file under 1 MiB so it could build diffs, and a baseline plus a live capture meant two such copies. The scan now has a diff-content pool, `STRICT_SCAN_CAPS.maxRetainedContentBytes`, set to 64 MiB per pass. It bounds memory and nothing else:

- Every included file is still read and hashed in full, whatever the perimeter weighs. The baseline always completes.
- Bytes that do not fit are dropped, not the file: the hash is still taken, so the file still enters the baseline digest and a later change in it is still detected. A full pool can never make a change look like no change.
- Binary content is dropped as soon as a NUL byte appears, before it can occupy the pool, since it could not be diffed in any case.
- A change in a file whose bytes were not kept is reported as `content_not_retained`: unreviewable, and therefore blocking `completed_clean`, exactly like a binary or an oversized change. It is a distinct reason from `over_file_size_limit`, which is about the file's own size rather than the workspace's.
- Exhausting the pool never ends a task, never needs a setting changed and never asks for a smaller folder.

**The report.** The report formatter still supports a short preflight report for non-chat callers. In the chat, a stop before any provider request now produces only one concise error reply with the reason and next step; it does not append a separate report. The full report remains for tasks that contacted a provider and states what the diff-content pool cost as a memory bound.

**What did not change.** The correctness invariants are untouched: the workspace digest and the per-file hashes, detection of changes between approvals and reviews, checks bound to the digest they ran on, cancellation, the pinned root descriptor, and detection of concurrent modification during a read. The path policy is untouched too: `.env`, `.ssh/`, `.aws/`, keys and certificates remain ordinary included files in Strict, and Balanced keeps refusing them, as decided earlier.

**Measured on a synthetic perimeter of the reported size.** A one-off probe outside the suite built roughly 310 MiB in 270 files — 220 text files of about 512 KiB each and 50 binary assets of 4 MiB — and scanned it with the real ceilings. The baseline took 346 ms and a capture 317 ms; the pool held 66,654,126 bytes of the 67,108,864 available; 144 files were hashed without keeping their bytes, 50 of them because they exceed the 1 MiB per-file limit and 94 because the pool was full; resident memory peaked around 222 MiB with a baseline and a capture alive at once. The folder that prompted this change was not read: the probe reproduces its declared volume with synthetic files.

That probe also shows the limit that remains. With more reviewable text than the pool can hold, some text files keep no content, and a change in one of them is reported rather than diffed. It costs a clean completion for that task; it never costs the baseline, the digest or the detection of the change.

**Regressions.** Five cases pin the behaviour, each exercising the branch rather than a nearby state:

- An 80 MiB perimeter completes its baseline and both captures, and a change inside one of its files is detected through its hash alone (`strictWorkspace.test.ts`).
- The same 80 MiB perimeter reaches phase A in a full task run, stopping at the planning capability gate with no limit breach recorded (`strictTask.test.ts`).
- With a pool far smaller than the text in the perimeter, the baseline still completes, retained bytes stay inside the pool, and files are recorded as dropped for the budget (`strictWorkspace.test.ts`).
- A file modified after its bytes were dropped is reported as changed, with differing hashes, `content_not_retained`, an unreviewable snapshot and an empty diff — and in phase B the same situation ends the task in `review_failed` / `unreviewable_change` before Codex is ever called (`strictWorkspace.test.ts`, `strictImplementationPhase.test.ts`).
- A preflight stop produces the short report, naming the failure, the untouched workspace and the next step, and containing none of the contract sections (`strictReport.test.ts`); a stop after the baseline still produces the full report.

What remains outside a guarantee: a change that lands between two captures is seen by the digest, and a change during a capture is prevented (directory redirection) or detected (file writes). Strict does not take a kernel-level consistent snapshot of the perimeter, and does not claim to.

Writing the first regression test for `runStrictTask` also exposed a defect no reviewer had reported: the function assembled its result without the `state` field, hidden by a type assertion, because no test had ever executed it. The result is now built in two explicit branches with no blanket cast.

After the ten rounds, the final sweep and these two product changes, on the same machine: `npm run compile`, `npm run lint` and `npm test` passed with **252 unit tests across 30 files**; all **7 local integration cases** passed; the rebuilt VSIX passed its **5 packaged cases**.

Still open: a manual click-through of the Strict plan gate, pause controls and report in the sidebar UI; the larger user workspace; and account/profile combinations not exercised by the temporary live turns. The deterministic adapter tests use fake runners, while the live turns recorded below also exercised real provider processes.

Live provider workflows and probes that send real prompts, modify temporary repositories or consume quota run manually with explicit authorization. CI stays mock-only.
