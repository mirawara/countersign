# Chat guide

Status: first version, verified on **Linux x64**. The Command Palette workflow stays available and is documented in the [workflow guide](workflow-guide.md); this page covers the sidebar chat.

## Requirements and installation

- **VS Code 1.106 or newer**; the sidebar and the packaged extension were exercised on VS Code 1.142.0 on Linux. A **trusted workspace with exactly one folder**. Git is optional, and files already present do not block a turn. Countersign never runs a reset, a commit or a clean for you.
- **Claude:** Claude CLI **2.1.109** verified, Agent SDK **0.3.306** used for Ask before change. The `claude` command must be on `PATH` or set in `countersign.claudeExecutable`.
- **Codex:** Codex CLI **0.163.0** verified. The `codex` command must be on `PATH` or set in `countersign.codexExecutable`. Both CLIs must be signed in for Balanced.
- **Node.js and npm** are needed to build or develop the extension, not to use an installed build. The provider CLIs must be present on the machine running the extension host.

From source: `npm ci`, `npm run compile`, then launch **Run Extension** in VS Code. For a local package: `npm run package`, then install `countersign-0.1.0.vsix` with **Extensions: Install from VSIX...**, and run **Developer: Reload Window** in the window you want to use. The package uses the Claude CLI already installed on the machine and excludes the SDK's optional bundled binary.

To open the chat, press **F1** (or `Ctrl+Shift+P`), type **Countersign: Open Chat** and press Enter. On a new installation the view appears in the **Secondary Side Bar** on the right; if that bar is hidden, press `Ctrl+Alt+B`. Windows that had already moved Countersign keep their previous placement: right-click the icon or the **Countersign** header → **Move To** → **Secondary Side Bar**. VS Code remembers the choice. If the command does not appear, check in the Extensions panel that **Countersign** is enabled for the current window or profile; in a remote window, check the remote extension host too.

## First conversation

The sidebar starts the Claude + Codex Balanced workflow. There is no one-provider chat or custom chat mode. Existing conversation history remains available after an update.

1. Run **Countersign: Open Chat** from the Command Palette.
2. Open **Turn settings** from the button above the composer. Choose a **Claude account**, a **Codex account**, their models and efforts, and **After plan approval: Ask before change** or **Full access**. **Current CLI login** uses the login already active in each CLI. **Add** imports an existing CLI profile directory or creates one and opens the CLI login in a terminal; **Sign in** reopens that login. Press **Refresh** after signing in. The picker checks every registered profile and displays the email reported by its CLI beside each choice; unavailable emails are labelled rather than guessed. An external login change needs another refresh. **Default (CLI)** delegates the model or effort choice to each CLI. The panel closes with its **×**, with `Esc` or by clicking outside it; the collapsed button shows the selected emails, models, efforts and permission. Turn settings and the draft survive closing or recreating the sidebar. The status line below the button shows the current workflow state and the time since its last update.

The account cards also show **plan usage** when a provider reports it: percentage used for each reported window, reset time when known, and when Countersign checked it. **Refresh** reads a new snapshot, and a completed task triggers another read. Codex uses its app-server rate-limit reply; Claude uses an experimental SDK control read of the subscription's `/usage` data. If either read fails or returns no windows, the card says usage is unavailable. These percentages can lag or disagree with a later turn's admission decision; they are not a remaining-token or remaining-request count. Per-task token estimates still appear in the report.
3. Describe the task and press **Start workflow** or `Ctrl/Cmd+Enter`. Claude prepares a read-only plan; review and approve it in the chat.
4. Your messages and the plan, questions, answers and final report remain in the thread. The header icons create a new thread, rename it, export a Markdown summary and delete it; the magnifier opens the search box over the thread list. **Countersign: Clear Chat History** deletes every thread in the workspace.

Local limits: 20 threads, 200 messages per thread, 100,000 characters of text per message. At 20 threads you must delete one before creating another; messages beyond the per-thread limit are dropped from the store. Search covers the titles and the text of the threads that remain.

Turn settings are saved in the workspace and restored after Reload Window, including mode, permission, model and effort. A temporarily missing CLI catalogue leaves a saved model or effort visible instead of erasing it. If VS Code reloads while a task is running, Countersign cancels and waits for that task during normal extension deactivation. The next host labels the saved reply **interrupted** and keeps any partial output; the old task cannot resume. A recorded `interrupted` or `finished` marker does not block the next task. A crash can leave an `active` marker: inspect the workspace and use **Countersign: Clear Strict interruption marker** only after confirming the old task is no longer active.

## Login and the first real turn

Sign in with the official CLIs — for example `claude auth login` and `codex login` — then confirm with `claude auth status` and `codex login status`. Countersign uses **the account already active in the CLI**, without reading, copying or storing tokens, cookies or API keys. If `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY` or `CODEX_API_KEY` are present in the environment, subscription-based chat stops: remove them from the extension host's environment and try again. Login, logout and revocation are handled by the providers.

The four model and effort selectors in **Turn settings** query the installed CLIs; **Refresh**, next to the account line in that panel, repeats discovery. A listed model can still be refused when the provider runs. Claude effort and Codex reasoning effort are separate settings, and an effort requires a selected model. The account line shows discovery status for both providers.

Choose a permission level before starting. **Ask before change** requests permission for edits, commands and network tools; **Full access** allows commands, network and external files without further prompts after plan approval. An approved command in Ask mode can also affect files outside the workspace. MCP remains disabled. The report and saved diff cover reviewable workspace changes, not external files or network actions.

Both permission levels require **Countersign: Verify Claude Settings Isolation** for the installed CLI version. Ask before change also requires **Countersign: Verify Claude Chat Isolation** for its Agent SDK path. Each gate runs controlled live requests and consumes Claude quota.

The composer sends the task text. To refer to a file, name its path in the task. Images and other binary attachments are not supported.

## Balanced workflow

**Claude + Codex (Balanced)** runs the real Claude and Codex pair. The model choice applies to that task only and does not change your global settings. Four selectors are available in **Turn settings**: **Claude model and effort**, and **Codex model and reasoning effort**. The lists come straight from the provider's own catalogue for your account, so each model offers exactly the levels it supports, with the catalogue's labels, and a new level appears as soon as a verified CLI version reports it. **Default (CLI)** leaves the choice to the respective CLI; to specify an effort you must first choose a model. **Refresh** reloads the catalogues. A listed model can still be refused by the provider when the request runs. If a model or a level you had chosen is no longer in the catalogue, the sidebar says so and the turn falls back to the CLI default for it rather than failing. Tools, local checks and timeouts continue to come from the VS Code settings.

In a dirty Git folder or a folder without Git, Balanced hashes small included files to compare later changes. The former 64 MiB total snapshot stop has been removed. At most 64 MiB per scan is retained in memory for patch construction; a change in a file without retained bytes is detected but cannot produce a reviewed patch. The 20,000 file count and per-file/diff limits still apply.

After **Start workflow**, Claude prepares a plan using read-only tools. If it needs a decision from you, the question appears in the thread: write your answer in the **Send answer** box. The plan and the execution details then appear in the thread; **Approve plan** starts the selected Ask before change or Full access execution, and **Cancel workflow** stops before implementation. The **Countersign: Start Workflow** command shows the plan in a modal dialog and uses the `countersign.executionPermission` setting.

During implementation, review or correction an agent can come back with a question. The workflow pauses between two CLI invocations and resumes after you answer in the chat. Partial changes are preserved, and the workspace diff is checked for external modification while it waits. A question cannot interrupt a single tool call already in flight. At most three questions are allowed during planning and three per execution phase; at the limit the workflow stops with the reason visible. **Stop** or **Cancel workflow** end the wait. Do not modify the folder while Countersign is waiting for an answer.

When it finishes, the chat keeps a **detailed report**: the approved plan, questions and answers, the phase history, the files changed, each check with its outcome and part of its output, the review with findings and evidence, the correction, and the usage the providers reported. **Show diff** on the report opens the stored patch. The report truncates very large output and findings; **Show Review Details** and **Show Check Results** show the full detail. Claude implements, Codex reviews the diff and Claude gets one correction pass; the negotiation to consensus is what **Strict** adds below. The sidebar says when a Countersign task holds the repository and disables starting another one. That lock covers a single extension host: separate VS Code windows are not coordinated yet.

## Strict mode

Open **Turn settings** and set **Mode** to **Strict** before sending. Balanced stays the default, and the choice belongs to that task: you can run a Balanced task and then a Strict one in the same conversation, and each message keeps its own label. The same model, effort and permission selectors apply. Strict has no per-task ceiling on changed files, and none on the size of the folder: the file-count and diff limits are the only limits on how wide a change may be. Strict scans all included workspace files, including `.env` and credential files, and their contents may be sent to the providers.

**Agreeing on a plan.** Claude drafts a structured plan with read-only tools. If it needs a decision from you, the question appears in the thread like a Balanced question; your answer becomes part of the plan, which changes its hash and cancels any approval already given. Claude and Codex then each approve, reject or revise that exact hash. A model's free prose is never taken as approval, and the hash it claims to have read is checked against the one Countersign computed.

**Approving it.** When both agree, the chat shows the plan, its hash and — when the plan can estimate it — how many files it expects. That estimate is information: nothing is blocked on it. In that card you switch between **Ask before change** and **Full access**, then **Approve plan**. **Refuse plan** ends the task without changing a file.

**Work and review.** A new Claude context implements the plan, your configured checks run, and a new read-only Codex context reviews the snapshot. Findings carry file, line and evidence; Claude answers each as fixed or disputed with a reason. Codex then approves the exact snapshot digest and Claude approves that same digest against the plan without write tools. If anything in the reviewed perimeter changes in between — including a check writing a reviewed file — both approvals fall and the cycle restarts on the new digest.

**Pauses.** After two cycles without verifiable progress the task pauses and the chat offers **Resume task** or **Stop task**. The pause exists only in this window: if VS Code restarts, the task is gone and you start a new one. Countersign stores a small lifecycle marker (task id, window id, mode, timestamp, outcome) and nothing that could resume or repeat a task. A normal Reload Window records interruption before the extension host exits, and that marker does not block the next task. A foreign `active` marker after a crash still blocks because the old task's state is unknown; **Countersign: Clear Strict interruption marker** removes it after confirmation.

**What you get.** Once a provider has been contacted, the report names the mode and the outcome with its reason and next action, every plan hash, the approvals, the baseline and every reviewed digest, the sessions and provider versions, the findings by status, the checks per round, the changes that were already in the workspace, the exclusions, the ceilings reached, the pauses and the marker state. If Strict stops before contacting either provider, the chat shows one concise error and next step instead of a report. A clean completion means: both providers agreed on one plan hash, you approved it, the configured checks passed, no blocking finding is open, both approved the same final digest, and nothing excluded or unreviewable changed. Anything else is a named failure. If nothing changed at all, the result is `no_changes` and the report says no final review happened.

**Ceilings.** Phase A: 8 provider requests, 20 active minutes. Phase B: 18 requests, 6 review cycles, 90 active minutes. No ceiling on changed files. One request times out after 10 minutes; an invalid structured answer is retried twice; the plan is capped at 64 KiB and a response at 128 KiB. Waiting for you does not consume the active budget, and the report shows calendar time separately. These numbers are **arbitrary placeholders**, not measurements: the measurement phase was skipped by decision.

**Workspace size.** There is no ceiling on how large the opened folder may be. Strict reads and hashes every included file in streaming, so a folder of hundreds of megabytes is scanned rather than refused, and you are never asked to open a smaller one. What is bounded is memory: the scan keeps at most 64 MiB of file contents per pass to build diffs. A file whose bytes did not fit is still hashed, so a change in it is always detected — it is reported as `content_not_retained`, which cannot be reviewed as a diff and therefore blocks a clean completion, just like a binary or a file over the 1 MiB per-file limit. The ceilings that can still stop a scan are 20,000 included files, 256 KiB of total diff and 16 KiB for a new file.

**Credential-shaped files.** `.env` and `.env.*`, `.ssh/`, `.aws/`, `.gnupg/`, `.npmrc`, key and certificate files are **not** special in Strict: they are scanned, hashed, diffed and may be sent to Claude or Codex as context, like any other file in the perimeter. That is a deliberate product decision — Strict reads the workspace it is asked to change. If a secret lives in one of those files, treat it as something both providers can see, and keep it out of the folder you open. Balanced is unchanged and still refuses those paths, so the two modes differ here on purpose.

## Quota, sessions and cancellation

Balanced calls Claude to prepare the plan, then calls Claude and Codex during implementation and review; corrections and configured checks can add work. Planning consumes Claude quota even if you decline the plan. The report shows provider usage when available. Dollar amounts are **estimates at API list prices**, not charges against your subscription. At a usage limit the workflow stops; no account switch happens. Strict calls both providers more often: a drafting turn, at least one evaluation each, then implementation, review and two final approvals, plus retries and corrections inside its ceilings. The two CLI profiles you select stay fixed for the task. To use another profile after a quota stop, select it manually before starting a new task.

Threads and reports live in VS Code's `workspaceState`. Reopening the sidebar is verified in the packaged extension, and rebuilding the store from saved data is covered by tests, but a full restart of an ordinary VS Code window has not been verified automatically yet. Old one-provider messages remain readable, while saved custom mode definitions are ignored. Diffs are local files in the extension's workspace storage and **can contain sensitive code**. Deleting a thread, or **Clear Chat History**, removes Countersign's messages and diffs; provider-native session data stays in the providers' own directories. A failed or cancelled workflow can leave partial changes: inspect the files and saved diff before starting again.

## Limits and troubleshooting

- Linux x64 is the only verified platform. Windows stays blocked because process-tree cancellation is not implemented there; macOS needs its own verification.
- The sidebar uses Codex model discovery, while Balanced and Strict review with the `codex exec` adapter.
- Strict completed a live `completed_clean` run with the real Claude and Codex CLIs in a temporary one-file repository. Manual packaged UI use and the larger user workspace remain unverified. An invalid structured answer is retried twice and then ends the task without agreement.
- Strict refuses to start when the installed providers cannot prove a fresh context or a read-only review sandbox, rather than trusting an instruction in the prompt.
- Organization-managed settings and a given model's actual capabilities can restrict tools and access further. If Claude refuses Full access, choose Ask before change or check the managed policy; plan approval cannot override it. A subscription login in the CLI does not certify future billing. Distributing a product that offers a Claude login requires clarification of Anthropic's terms — see [third-party-accounts.md](third-party-accounts.md).
- After a workflow that changes files, the chat stores a Git diff against `HEAD` in a clean repository or a diff against the initial file snapshot in a dirty repository or a folder without Git. Git-ignored files or generated directories (`node_modules`, `dist`, `build`, `coverage`, `.cache`, `.venv`, `target`), binaries and excluded paths are not included, although a provider may still have touched them.
- If a provider has no models, check workspace trust, a single open folder, the CLI versions, the official login and the API-key environment variables, then press **Refresh**. For the older workflow, use **Show Diagnostics**. The chat never writes prompts, credentials or diffs to the Output Channel.

Reproducible live probes live in `scripts/smoke-chat-adapters.mjs`, `scripts/smoke-chat-write.mjs`, `scripts/smoke-claude-path-policy.mjs`, `scripts/smoke-codex-approval.mjs` and `scripts/probe-codex-app-server.mjs --live --full-access-probe`. They require `--live`, consume quota and run only against temporary repositories. `npm test` and the packaged `chat-mock` case send no real prompt.
